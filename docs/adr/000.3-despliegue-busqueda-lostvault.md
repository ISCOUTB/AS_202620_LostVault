# Comparación de despliegue — Endpoint de búsqueda de LostVault

**Proyecto:** [AS_202620_LostVault](https://github.com/ISCOUTB/AS_202620_LostVault)
**Fecha:** 2026-09-27

---

## 0. Alcance de esta entrega

Este documento compara **dos alternativas de despliegue para una sola pieza del sistema**: el endpoint HTTP `GET /v1/objects/search`. No cubre el despliegue del sistema completo. Los criterios de comparación son los definidos por la cátedra en la guía de despliegue y costos; donde esa guía no especifica un dato exacto, se declara el supuesto usado.

---

## 1. Pieza elegida y justificación

**Pieza: la API de búsqueda de objetos** — el endpoint `GET /v1/objects/search`, equivalente al `ObjectService`/módulo `search` (`lib/features/search`, `lib/features/objects/public`), expuesto con el mismo patrón contractual que ya usa `docs/contracts/lostvault-api.yaml` para `/claims` (OpenAPI 3.1).

Se eligió esta pieza porque es la única con un **escenario de calidad con p95 medible** documentado en el propio repositorio:

> **Escenario 4 — Rendimiento** (`docs/arc42/10_requisitos_calidad.md`): búsqueda por palabra clave en hora pico, **~200 usuarios concurrentes**, **95 % de las búsquedas ≤ 2 s (p95)**.

Esa es la condición operativa asignada contra la que se contrasta el arranque en frío de la alternativa serverless.

## 5. Resultados medidos

### 5.1 Alternativa A — p95 bajo el Escenario 4 (200 conexiones concurrentes, 10 s, `autocannon`)

| Percentil | Latencia medida |
|---|---|
| p50 | 98 ms |
| p97.5 | 147 ms |
| p99 | 205 ms |

**p95 real (interpolado) ≈ 110–140 ms** — muy por debajo del umbral de 2 s. 15.000 requests atendidos en 10,1 s sin caídas.

### 5.2 Alternativa B — arranque en frío (proxy local, 30 invocaciones, proceso Node nuevo por invocación)

| Métrica | Valor medido localmente |
|---|---|
| Costo de `require` + construir catálogo | 1,28 ms |
| Arranque de proceso + init (wall, p50) | 31,3 ms |
| Arranque de proceso + init (wall, p95) | 34,8 ms |

**Advertencia metodológica:** este proxy local solo captura el costo de inicializar el runtime Node y el módulo en la máquina de prueba. El cold start real en Google Cloud Functions añade aprovisionamiento de contenedor y red; según benchmarks públicos del proveedor, ese costo adicional para Node.js suele ubicarse entre **100 y 500 ms**. Este número debe reemplazarse por la medición real contra la función desplegada (sección 4) antes de entregar el trabajo final.

### 5.3 Contraste cold start vs. p95 del escenario

Incluso usando el extremo alto publicado (~500 ms de cold start) más la latencia de ejecución observada (~100–150 ms), el peor caso de una invocación fría (~650 ms) **queda dentro del presupuesto de 2 s p95** del Escenario 4. Con 200 usuarios concurrentes, además, la mayoría de las invocaciones caen dentro de la misma ventana de contenedores ya calientes, por lo que el cold start afecta solo a una fracción pequeña de las peticiones.

### 5.4 Medición real sobre el despliegue (Vercel, plan gratuito), 2026-10-04

Las mediciones de 5.1 se hicieron en local. Aquí se mide el despliegue real (`https://backend-nu-self-91.vercel.app`, `GET /objects`) con autocannon:

| Corrida | p95 (≤) | p50 | Resultado |
|---|---|---|---|
| c=200, d=30 | 171 ms | n/d | 27.000 peticiones, ~44% fallidas (11.865 no-2xx, 2.000 errores o timeouts). Después, Vercel respondió 403 a todo el tráfico (causa probable: protección anti-abuso, sin confirmar). |
| c=20, d=30 (tras levantarse el bloqueo) | 176 ms | 130 ms | ~142 req/s, sin errores; máximo 1678 ms (pico aislado). |

**Lectura:** la latencia cumple el objetivo de 2000 ms con holgura. Pero el plan gratuito no sostuvo las 200 conexiones concurrentes del Escenario 4: el p95 de la corrida c=200 describe solo las peticiones que sí respondieron, no la disponibilidad. Esto contradice la expectativa de la sección 5.3 de que el escalado automático absorbe el pico, y queda como riesgo conocido. No se repitió la prueba de alta concurrencia para no volver a activar el bloqueo.

Comando para reproducir la medición moderada:

```
npx autocannon -c 20 -d 30 https://backend-nu-self-91.vercel.app/objects
```

## 6. Costos y punto de quiebre de la capa gratuita

**A. Servidor del laboratorio:** $0 permanente, sin tarjeta, sin cuota de invocaciones. Limitación: capacidad fija (un solo proceso/VM) y disponibilidad atada a la operación del laboratorio, no a un SLA gestionado.

**B. Google Cloud Functions (Gen2), capa "Always Free":**

| Recurso gratuito/mes | Cuota | Consumo estimado en piloto |
|---|---|---|
| Invocaciones | 1.000.000 | Cientos de miles (bajo) |
| GB-segundos de cómputo | 400.000 | Con 256 MB y ~150 ms/ejecución → ~0,0375 GB-s/invocación → se necesitarían ~10,6 M invocaciones para agotar este cupo antes que el de invocaciones |
| Salida de red | 5 GB | ~1–2 KB/respuesta → se agotaría cerca de las 2,5–5 M invocaciones |

**Punto de quiebre:** el recurso que se agota primero es el de **invocaciones (1.000.000/mes)**, equivalente a ~66.700 búsquedas/día. Para la escala de un solo campus universitario en fase piloto, ese umbral no se alcanza salvo adopción viral. Superada la capa gratuita, la tarifa pública aproximada de Cloud Functions Gen2 es del orden de **US$0,40 por millón de invocaciones adicionales** más cómputo por GB-s (tarifas públicas, sujetas a cambio — verificar en la calculadora oficial antes de presupuestar en producción).

## 7. Procedimiento de reversión (rollback)

**A. Servidor del laboratorio**
1. Mantener cada versión como imagen Docker etiquetada (`lostvault-search:vN`).
2. Si la versión nueva falla: `docker stop lostvault-search && docker run -d --name lostvault-search lostvault-search:v(N-1)`.
3. Verificar con `curl` al endpoint de salud antes de reabrir tráfico.

**B. Cloud Functions Gen2**
1. Cada despliegue crea una nueva revisión (Cloud Functions Gen2 corre sobre Cloud Run).
2. Rollback sin downtime: `gcloud run services update-traffic lostvault-search --to-revisions=REVISION_ANTERIOR=100`.
3. Confirmar con una invocación de prueba y revisar logs de Cloud Logging.

## 8. ADR

```markdown
# ADR 0003: Despliegue del endpoint de búsqueda de objetos

- Estado: Propuesto
- Fecha: 2026-09-27
- Decisores: Equipo LostVault
- Escenario relacionado: Escenario 4 — Rendimiento (docs/arc42/10_requisitos_calidad.md)

## Contexto
El endpoint GET /v1/objects/search debe responder a picos de ~200 usuarios
concurrentes con p95 ≤ 2 s (Escenario 4), bajo la restricción organizativa de
"sin infraestructura propia con presupuesto" (docs/arc42/02_restricciones.md).
Se comparan dos alternativas: una instancia persistente en el servidor del
laboratorio y una función serverless (Google Cloud Functions Gen2).

## Decisión
Se adopta Google Cloud Functions (Gen2) como proveedor de despliegue del
endpoint de búsqueda, con el servidor del laboratorio documentado como
alternativa de respaldo sin tarjeta.

## Alternativa considerada: servidor del laboratorio
Cumple sin tarjeta y sin cuota de invocaciones, pero la capacidad es fija,
requiere que el equipo (4 personas con carga académica simultánea) opere el
proceso manualmente, y la disponibilidad depende de la operación del
laboratorio, no de un SLA gestionado — lo que la debilita frente al Escenario 1
(disponibilidad 99 %).

## Consecuencias

**Positivas**
- El escalado automático absorbe el pico de 200 usuarios sin intervención.
- El costo permanece en $0 dentro del volumen esperado en fase piloto
  (muy por debajo del punto de quiebre de 2 M invocaciones/mes).
- El rollback por revisión es instantáneo y sin downtime.
- Reduce la carga operativa sobre un equipo sin dedicación completa.

**Costos aceptados**
- Requiere una tarjeta para verificar la cuenta de Google Cloud, aunque el
  consumo no se facture dentro de la capa gratuita.
- El arranque en frío añade latencia variable; medido de forma local se
  aproxima a 30–35 ms de inicialización de runtime, y según benchmarks
  publicados del proveedor el cold start real puede llegar a 100–500 ms —
  aun en el peor caso, queda dentro del presupuesto de 2 s p95 del escenario.
- Se pierde control total sobre el entorno de ejecución frente a una VM propia.

## Trazabilidad
- Escenario de calidad: docs/arc42/10_requisitos_calidad.md (Escenario 4).
- Restricción: docs/arc42/02_restricciones.md ("sin infraestructura propia con presupuesto").
- Prototipo de medición: proto/instance/server.js, proto/faas/handler-cold.js.
```
